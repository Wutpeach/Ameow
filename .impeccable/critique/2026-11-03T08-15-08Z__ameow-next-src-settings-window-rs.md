# Ameow Next 设置界面设计评审

2026-11-03 · Impeccable Skill 4.8.0 / engine 0.1.18。目标：`ameow-next/src/settings_window.rs`，关联 `settings_components.rs`、`tokens.rs`。

**结论：现有视觉风格成立，与当前 PRODUCT.md、DESIGN.md 和设置 Surface 简报基本一致；优化应集中在组件页的状态层级与键盘可达性。** 本次提出 4 项：1 项 P1、2 项 P2、1 项 P3，无 P0。建议先做 1、2，再做 3，4 可随局部打磨处理。

## 证据与范围

实际覆盖：浅色/深色下的常规、下载、组件与诊断、关于；组件页上下滚动；检查更新的加载与成功结果；中英文布局；选择器、方向键/Enter、Esc、Tab/Shift+Tab；长路径点击复制及反馈。Windows 96 DPI（100%），截图客户区 564×431。文件夹选择器曾打开，但用户同时操作过鼠标，其退出/取消过程不计入已验证结果。

隔离配置中实际出现“组件准备失败 / 组件来源返回错误”。该状态用于评估失败态呈现，未定位其后端原因，也不据此认定正常安装必然失败。没有执行组件升级、恢复、重试准备、下载任务或开机启动切换。评审进程已通过 CloseMainWindow 正常退出。

## 设计判断与值得保留的部分

设置窗口符合 Ameow 的“紧凑、安静、实用”定位。它采用熟悉的桌面偏好布局，品牌个性比主浮窗弱一些，这是合适的职责分配；不需要加大面积品牌色、装饰卡片或营销式标题。原生界面不适用 Web detector，本次未运行检测器。

1. **清晰且稳定的骨架。** 128 宽侧栏、24 内容内边距和固定对齐线让四个分类容易理解；浅深主题的布局、层次与控件位置一致。
2. **字号和控件尺度合适。** 20/28 标题、14/20 正文、13 控件和 12 辅助文字各司其职；32 高按钮、36 高导航、6 圆角形成统一语言。系统字体用于设置，路径和版本保留等宽字体，理由充分。
3. **反馈足够克制。** 更新检查有“检查中…”、禁用及独立结果区域；语言/主题切换直接生效；可见控件的键盘焦点清楚。下载与关于页的留白符合内容量，无需为了填满窗口而压缩或增加内容。

## 优先问题

### 1. [P1] 组件页焦点进入屏外后，页面没有跟随滚动

**依据：交互已确认，截图留证，源码支持。** 组件页处于顶部且展开检查结果后，从“检查更新”连续按 Tab，会依次进入下方“复制诊断”和“重试准备”，但视口不动，焦点框消失。手动滚到底部，能看到“重试准备”的蓝色焦点框。没有触发重试动作。

**位置与原因：** `settings_window.rs:1207` 通过 `focus_next/focus_prev` 切换焦点，`settings_window.rs:1262` 的滚动区没有随焦点目标进入可视区的处理。控件已可聚焦，问题在焦点与滚动的联动。

**影响：** 键盘用户无法知道当前动作是什么，可能在不知道目标的情况下按 Enter；失败恢复路径受影响。

**建议：** 焦点切入滚动内容时，只滚动足够距离，使目标及焦点框完整可见；保留现有 Tab 顺序和焦点样式。验证正反向 Tab、首尾循环，以及检查结果或确认区域展开后的动态高度。建议命令：`impeccable harden`。

证据：`keyboard-components-tab-3.png` → `keyboard-components-tab-4.png` → `keyboard-components-tab-5.png`；反向回到该焦点后手动滚动的 `keyboard-components-focused-below-fold.png`。

### 2. [P2] 组件失败与恢复入口排在信息末尾，首屏看不到

**依据：截图直接确认，滚动交互确认。** 初始首屏先显示三个组件的“不可用”，以及 yt-dlp 来源、策略、准备规则。明确失败原因和“复制组件诊断 / 重试组件准备”在下方，首屏仅露出按钮边缘；画面没有清楚的滚动提示。检查结果展开后，诊断区进一步下移。

**位置与原因：** `settings_components.rs:258` 的策略说明和检查结果先占据空间；全局诊断和错误在三项组件之后才追加（`:573`）。源码有纵向滚动，但当前画面未提供明显的滚动轨道/提示。

**影响：** 用户先读到“版本管理”，之后才发现当前任务其实是“排除准备失败”。检查更新成功也不代表组件准备成功，两类状态需要更明确地区分。

**建议：** 失败时，在标题下面优先显示紧凑状态摘要与对应恢复入口；详细诊断、来源和策略仍留在原有分组中。内容溢出时提供轻量滚动条或明确的下方内容提示。保留现有真实可用性、pending、cooldown 和确认边界，避免新增自动重试。建议命令：`impeccable layout` / `impeccable clarify`。

证据：`light-components-top.png`、`light-components-bottom.png`、`dark-components-check-result.png`。

### 3. [P2] 浅色模式的 12px 错误正文对比度偏低

**依据：真实截图像素测量与源码一致。** 浅色诊断区的两行错误正文使用 `#E3474C`，白底 `#FFFFFF`，对比度约 **3.98:1**，低于普通小字常用的 4.5:1 可读性参考。深色对应组合约 4.68:1，不能把两种主题一并判为相同问题。这里是局部文字对比度测量，不是整应用的无障碍合规结论。

**位置与原因：** `settings_components.rs:600`、`:608` 使用 12px 文本直接配 `p.red`；`tokens.rs:79` 的浅色状态红同时承担了小字正文的职责。

**影响：** 最需要用户阅读的错误信息，比常规正文更难辨认，尤其对低视力用户。

**建议：** 给浅色错误正文使用更深的语义文字色，或用正常高对比正文配红色标记，仍保留明确的错误文字。无需全局修改进度环、状态图形或整套 Palette。建议命令：`impeccable colorize`。

证据：`light-components-bottom.png` 与 `dark-components-bottom.png`；测量使用错误文字实色像素，未把抗锯齿边缘当作前景色。

### 4. [P3] 长路径可以复制，但缺少事前可见的复制提示

**依据：截图与点击交互确认，tooltip 内容来自代码检查。** 路径显示为中间截断的浅底信息条，旁边只有“打开 / 更改”。点击路径会成功显示“完整路径已复制 / Full path copied”，但点击前没有复制图标或文字。

**位置与原因：** `settings_window.rs:974` 起的路径条同时是值展示和复制操作；hover tooltip 只提供完整路径，没有说明复制动作。它并非不能查看或复制完整路径，而是功能不易发现。

**建议：** 在现有路径条内加入克制的复制图标或短提示“复制完整路径”，保留整条可点击、键盘操作与成功反馈，不必再加一排按钮。建议命令：`impeccable clarify` / `impeccable polish`。

证据：`dark-english-download.png`、`dark-english-path-copied.png`。

## 认知负荷、情绪与用户视角

认知负荷检查 8 项中，主要弱项是组件页的**视觉优先级**与**按需展开**，约 2 项，属中等负荷；常规、下载和关于页负荷低。导航只有 4 个选项，选择器各 3 项，未发现需要同时比较超过 4 个选项的决策点。问题不是选项过多，而是故障信息出现得太晚。

日常设置过程平静、反馈直接；故障时却先看见“不可用”和版本信息，滚动到底部才出现下一步，这段情绪落差应优先消除。

- **Sam（键盘 / 低视力用户）：** 在检查按钮之后丢失可见焦点；浅色小号错误字对比不足。
- **Jordan（初次处理故障）：** 可能把“上游版本检查成功”理解为组件已恢复；失败摘要与恢复入口应并置。
- **Alex（频繁整理素材的熟练用户）：** 复制下载目录的能力存在，但路径条外观不能直接说明这项快捷操作。
