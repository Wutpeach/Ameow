# Ameow 代码健康与架构审查

用户要求梳理代码结构、清理冗余、评估 Windows/Mac 共用或检查多轮改动累积时读取。此处先在 Ameow 试用；协作、授权、并行与交付沿共享 Ship。日常小修仍按其实际影响执行。

## 建立可审的范围

先确定本次基线、关注的用户流程和期待改善。适合在一批功能稳定后集中审查；主线仍有修复或发行工作时，核写入责任和实际依赖，以明确隔离的范围推进。保护当前 dirty、原失败、用户数据、已签资产与其他任务输入，避免把清理源码和回收资源混作一项操作。

先研究现有 AGENTS、相关 OpenSpec、模块调用关系与近期改动，逐项区分源码事实、历史理由和推断。沿实际调用方追踪重复规则、跨模块共享状态和特殊分支，不把文件长、行数多或一次平台搜索无命中直接判为冗余。

## 本项目重点

- **任务状态与资源归属**：提交、解析、传输、处理、交付、取消、Held、退出和重启由谁推进，何时释放槽与文件租约；追踪 `src/download/`、control 与 UI 之间的状态传递。
- **Windows/Mac 共用边界**：相同意图、合同和业务规则应有清楚归属；进程、窗口、权限与原生操作按平台实现。合并以语义和调用关系一致为依据，保留实际差异。
- **App、CLI、Host 与扩展**：核对是否复用真实业务入口，是否出现多套偏好、队列、组件或维护规则，以及协议边界是否仍能独立解释和验证。
- **重复与历史分支**：确认生产、平台 cfg、测试夹具、预览、迁移与旧生产消费者的用途，再提出删除或合并；完成调用方迁移后收掉失去用途的内部兼容路径。
- **启动与重复工作**：按需要测量组件准备、完整性检查、状态查询、轮询、文件 I/O 与进程启动成本。说明样本、瓶颈和覆盖，不能从减少代码行数推出性能收益。

进程所有权、受信运行时、取消证明和发行完整性守卫保留其正式含义。确需改变行为或信任边界时，按项目 OpenSpec 工作流明确方案；复杂但承担必要约束的实现应先理顺职责和可读性。

## 把发现变成值得实施的工作

给来源伙伴一份经过筛选的优先清单：具体位置与证据、实际维护或用户影响、建议整理范围、受影响调用方/平台、验证方式。区分现在值得做、可随相关改动处理、保留现状更合适及证据不足，不以问题数量或抽象层数作为成果。

实施沿已有授权，以可独立验证的小批次组织。跨模块或共享接口变更明确整合者；并行研究可按独立问题划分，写入按文件和依赖隔离。同一业务规则的迁移覆盖真实调用方，避免半套新接口长期留给后续任务猜测。

## 验证整理的结果

以已确认产品行为、正式规范和实际调用合同检查回归，复用未变范围的有效证据。按改动选择定向用例、default 构建输入以及两平台必要实跑；平台专属 cfg 与异常收尾不由另一端编译成功替代。性能改动保留可比基线与前后测量，结构整理主要核职责、状态归属和后续修改是否更易理解与验证。

方法索引或验证脚本随实现更新；代码审查报告和本轮结果留既有 handoff，不生成第二套长期状态账本。总结实际删除/合并与理由、得到的改善、验证范围和仍需保留的边界。试用后再把跨项目成立的方法提炼进 Ship，Ameow 保留本项目重点和入口链接。
