# Ameow 用户文档与公开文案

编写 README、手册、演示、Release 或 Changelog 时读取。先确定读者此刻要理解或完成什么，再选择必要文字和现有主题组件。清晰、准确、可扫读优先于单纯追求字少；本 reference 是写作约定，不另建 docs/content-style.md 或平行写作入口。

## 内容职责

| 内容 | 应说明什么 |
| --- | --- |
| README | 产品用途、重要能力、下载/手册入口与最短上手；配真实产品演示，保留必要文字。 |
| 使用手册 | 当前可用操作、步骤、结果和必要恢复方式；复杂细节按需展开，功能历史集中到 Changelog。 |
| Release / Changelog | 相对上一正式版的关键新增、改进与修复，以及本次升级和下载选择。 |
| 开发与交接报告 | 构建来源、源码/哈希、CI、验收覆盖、失败前驱及实现过程，留在工程记录。 |

## 写法与信息层级

- 依据已接受界面的可见控件文字、平台条件和实际结果，直接说用户能做什么、怎样操作、会得到什么。术语只有帮助识别实际选项时才保留，必要时就地解释。
- 标题、正文、步骤、代码框和提示各有用途：命令用真实代码框，操作流程用步骤，关键限制用简短提示。群通知等精简稿保留功能分组和必要升级动作；不把所有段落做成卡片，也不用大段正文替代结构。
- UI 的少冗余原则不等于手册禁止解释；手册的解释也不全部常驻到按钮和设置项下方。实际设计 token 归 DESIGN / sidecar，正式行为归 OpenSpec。
- README 稳定介绍当前能力，不反复写“旧版还没有/候选等待/下一版预览”。保留必要兼容性、实际下载 URL 与版本查询命令；尚未发布的能力与正式用户路径明确区分。
- 普通用户页面不叙述候选、内部 PR、朋友测试包、特殊 token、用户验收或证据矩阵。真实产品限制要保留，说明用户影响和可行操作。
- 中英文表达同一事实。新增 CLI 要说明实际新增能力；授权或同步续接不能扩大为失败下载自动重试，性能样本不能变成固定提速承诺。

整理 Release / Changelog 时，核从上一正式版到本次候选的完整变化和已交付能力，区分新增与改进，不只复用上一份草稿或最后一项修复摘要。

## 下载说明与演示

先给人类下载入口，再解释机器更新文件。按本次真实包成员说明 Windows 安装版、完整便携版，以及 Mac 完整 App 的安装方法。0.5.2 起 Windows 完整便携包兼作后续应用内更新载荷，不再另发单程序更新 ZIP；0.5.1 的两种 ZIP 仍按历史用途说明。保留本次完整重新安装和扩展安装/重载/网页刷新的必要步骤；不将完整便携包误写成缺功能，不因名称相近混淆历史包用途。整理展示不改变已发布旧版资产。公开资源发布前，下载链接继续指向现有可用资源。

README 用真实产品界面演示质感，手册可用忠实简化原型说明操作。只保留当前理解必需的控件名称和取值，保留真实操作与结果，不能精简成无意义骨架。遵循已有用户决定：演示自动循环、手动操作后闲置恢复和低动效路径；不无故增加一套播放控制。看实际连续渲染，静态结果不证明动效通过。

## 审阅与检查

执行方先核事实、受影响链接和相应渲染；伙伴按完整页面核可读性，再将稳定的重要稿件交用户最终审阅。用户是第一位实际使用者，技术检查、模型审核和“用过 Skill”不能代替其确认。实质修改补审相关部分，已认可同版内容不重复批准；体验交付见 [acceptance.md](acceptance.md)，正式公开步骤见 [release.md](release.md)。

网页检查的预期来自已审稿件、页面职责和真实入口；失败时先区分内容缺陷与检查预期错误，再修正对应一侧。

文案修订只做相应内容、链接和渲染检查，不触发产品构建、全套 CI、签名或制包。复用 `site/scripts/verify-build.mjs` 的生成页面、双语路由、本地链接/资产/片段校验；它由 `site/package.json` 的 build 调用，不为写作新造检查工具链。需要站点完整构建时沿用现有入口和 Node 版本要求，先核本轮授权与影响。Pages 部署仍由原工作流负责。

Ameow Docs Sync 已退役，文档随获授权的开发、文档或发布任务维护。`.ameow-docs-reviewed-state.json` 是保留的历史审阅/失败记录；其中旧 pending 与 PR53 不作为恢复自动化或继续修补该 PR 的指令，不推进旧游标，也不因停用自动化清理原 dirty。
