# Design

## Context

见 proposal.md。现有 Inno 以 state 存在但 entry 缺失拒绝旧布局；完整版本由启动器验签登记，已有同签名版本幂等处理。卸载日志不能覆盖安装后经应用更新增加的版本及每用户数据。

## Goals / Non-Goals

保持完整版本事务、用户文件、真实签名和既有每用户数据域。维护入口复用当前启动器及 Rust 路径/签名校验，不新增生产签发或缓存迁移。

## Decisions

- Inno 调用随已验签载荷携带的新启动器维护入口。辅助副本以临时名称运行，避免安装/卸载时锁住稳定入口；编译脚本仍从单一 verified payload 取字节。
- 旧布局先识别和备份安装状态、过时入口，再转换；失败恢复备份，成功仍由新版本真实 Ready 决定已接受版本。无需旧版先行卸载时直接转换，避免先拆除可用程序。
- 卸载扩展清理通过已签名版本清单与精确接线归属产生目标集合，不对整个安装目录递归删除；保留未知文件。用户数据只清理当前明确告知的自有条目，拒绝重解析点，多副本优先保留共享数据。
- 原生卸载选择默认保留，silent 路径也保留。自有 fixture 使用独立 AppId、注册命名空间及隔离数据域；不借 fixture 访问默认真实数据。

## Risks / Trade-offs

- 旧目录可能由手动组合而来 → 无可靠身份时保留并给具体失败与恢复路径。
- 文件占用或权限可能导致部分清理 → 禁止强杀，报告准确剩余项目。
- 没有可用的中文 Windows 账户或生产旧消费者隔离入口 → 分别保留实际覆盖与未知，不以 Unicode 单测代替整链路。

## Migration Plan

只改 0.5.3 源码与新候选。先定向测试维护策略及完整性边界，再在获得本机重任务槽后用自有安装/注册/快捷方式验证实际流程。用户最终从根 main 使用 cargo run 验收应用，安装交互另提供自有候选证据。
