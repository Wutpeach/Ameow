# Research: compact ear-root occlusion model

- Query: Trace the current Compact mascot from its canonical definition through avatar-core projection, Ameow scene/component composition, SVG emission, and paint ordering; determine whether the existing path can hide only ear-root pixels inside the circular body while retaining the current ear geometry and pose.
- Scope: internal (Ameow sources, pinned bible-strong source checkout, installed package/runtime/types/source maps); no alternative ear geometry or renderer was evaluated.
- Date: 2026-09-09 (Asia/Shanghai)

## Findings

### Actual rendering path

1. `src/presentation/main-window/compactMascotDefinition.ts:49-62` is the canonical `AvatarDefinition`: a 240x240x240 sphere plus exactly two 76x135x78 diamond nodes at `[-70,-76,-82]` and `[70,-76,-82]`, with mirrored rotations. It is validated before export at `:83-86`.
2. Avatar-core converts definition nodes to runtime `BodyNode`s (including generated `runtime-node-0/1` ids) in `.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/scene.ts:37-46`. `renderAvatarDefinition` resolves the expression and calls `renderAvatarExpression`, which calls `renderAvatar(..., { bodyNodes: body.nodes })` at `.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/scene.ts:53-79`. Animated `renderAvatarFrame` samples the playback/pose and reaches the same scene helper at `.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/runtime.ts:337-348`.
3. Ameow’s `renderCompactMascotScene` samples the current frame/pose, calls core once with `BODY.nodes: []` for head/eyes and once with `BODY.nodes` for ears, then copies the second call’s node arrays over the first geometry at `src/presentation/main-window/compactMascotBehaviorRuntime.ts:32-53`. The behavior test confirms head/eye paths and the combined ear arrays equal direct core output across retained action times (`src/presentation/main-window/compactMascotBehaviorRuntime.test.ts:37-63`).
4. `CompactMascot` initially obtains the scene through `renderAvatarDefinition` (`src/presentation/main-window/CompactMascot.tsx:57-63`), updates fixed ear/head/eye path slots from `AvatarScene` (`:65-89`), and emits one SVG. Its DOM order is back ear 0, back ear 1, head, eye group, front ear 0, front ear 1 (`:180-208`). The eye group alone uses a `clipPath` whose path is the core `headPath` (`:180-205`).
5. Production mounts this leaf at `56 * 0.95` inside the unchanged Compact shell (`src/presentation/main-window/MainWindowPresentationSurface.tsx:1191-1243`); the Lab mounts the same production leaf and 56px geometry (`src/lab/CompactPreviewStage.tsx:131-155`).

### 1. Path completeness and depth/order

- Yes: the primary body is one complete closed `headPath`. Core’s sphere/ellipsoid path is emitted as a closed SVG path by `ellipsePath` (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:912-928`) and selected by `headPath` (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:1120-1153`). Each `BodyNode` is also one complete independent closed path: `accessoryPath` samples the full 17x49 node surface, applies local rotation/position, shared pose, and perspective, then convex-hulls/smooths the projected points (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:1155-1191`). The generic formatter closes paths with `Z` (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:461-467`); it does not output hidden/visible fragments.
- Depth/order is per node, not per surface sample or fragment. `accessoryLayers` creates one `{ id, path, depth, front }` record per input node, computes `depth` from the rotated node position, uses a single center-depth threshold (`front: depth > accessoryCameraDepthRadius(...) * 0.1`), sorts by that depth, and partitions whole paths into `backPaths`/`frontPaths` with matching node-id arrays (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:1193-1234`). `renderAvatar` returns those complete arrays plus `headPath` (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:1237-1260`). The projected surface samples affect the outline, but their individual camera depths are discarded by the hull; there is no true surface/fragment depth test.
- The installed runtime matches this contract: `node_modules/@bible-strong/avatar-core/dist/geometry.js:672-701` contains the same one-record layer, center-depth sort, and complete `backPaths`/`frontPaths` output. The neutral Compact assertion expects two back paths and zero front paths (`src/presentation/main-window/compactMascotDefinition.test.ts:35-40`), and the path assertions require two non-empty paths (`:59-63`).
- The SVG painter-order primitive is already a partial visual clip for a back node: a complete ear path painted before the opaque `headPath` is overpainted wherever the two silhouettes overlap, leaving only the ear pixels outside the body visible (`src/presentation/main-window/CompactMascot.tsx:185-191`). No fragment path is needed for that all-behind case.

### 2. Behind-head authority split

- Geometry/projection authority is avatar-core plus the Ameow definition inputs. Core owns primitive sampling, local node transform, shared pose rotation, perspective projection, closed path generation, and the binary node layer classification (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:1155-1234`). Ameow owns the canonical dimensions/positions/rotations and selects which core call supplies head versus node arrays (`compactMascotDefinition.ts:49-62`; `compactMascotBehaviorRuntime.ts:34-51`), but does not calculate a head/ear intersection.
- Paint/composition authority is Ameow’s SVG host. Back paths are painted before the opaque head path, so the head overpaints any overlapping pixels; front paths are painted after it and therefore remain fully visible (`CompactMascot.tsx:185-207`). This painter order is sufficient for the requested silhouette whenever an ear is kept in `backPaths`; it is not core occlusion geometry. The observed pose failure is that core can dynamically classify a whole node as front from center depth and hand the complete path to `frontPaths` (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:1217-1234`), after which this host intentionally paints it over the head.
- The core contract exposes no stable per-node behind-head/layer override: `AvatarGeometry` contains only complete path arrays and their node-id arrays (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:49-60`), while `RenderAvatarOptions` has only `includeWire`, `bodyNodes`, and `eyeOffset` (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:62-66`). The ids are carried through Ameow’s scene merge (`compactMascotBehaviorRuntime.ts:47-50`), but the current host assigns paths by array index and does not read those ids (`CompactMascot.tsx:67-70`).
- The inner shell panel clips descendants to the current shell boundary (`MainWindowPresentationSurface.tsx:1151-1166`; Lab equivalent `CompactPreviewStage.tsx:131-145`), but that is viewport/shell clipping, not the circular `headPath` silhouette. The mascot SVG itself is explicitly `overflow: "visible"` (`CompactMascot.tsx:166-178`).

### 3. Existing reusable clipping/occlusion capability

- Installed package version is `@bible-strong/avatar-core` 0.1.0 (`package-lock.json:314-324`; `node_modules/@bible-strong/avatar-core/package.json:30-51`). Its public geometry declaration exposes only `backPaths`, `frontPaths`, node-id arrays, `headPath`, eye paths/visibility, and `wirePaths` (`node_modules/@bible-strong/avatar-core/dist/geometry.d.ts:35-54`); `RenderAvatarOptions` has only `includeWire`, `bodyNodes`, and `eyeOffset` (`node_modules/@bible-strong/avatar-core/dist/geometry.d.ts:47-54`). `AvatarScene` is only `{ geometry, colors }` (`node_modules/@bible-strong/avatar-core/dist/scene.d.ts:6-17`).
- The actual installed bundle implements the same contract (`node_modules/@bible-strong/avatar-core/dist/geometry.js:672-701`), and `node_modules/@bible-strong/avatar-core/dist/geometry.js.map:1` embeds `../src/geometry.ts` source content; `node_modules/@bible-strong/avatar-core/dist/index.js.map:1` embeds the scene/runtime sources. The pinned source implementation has no mask, clip, occlusion, silhouette subtraction/intersection, or fragment output in the render path (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:49-66, 1155-1260`; `.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/scene.ts:48-79`). The v1 node type/schema likewise permits only `surface`, `position`, and `rotation` (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/avatarDefinition.ts:50-59`; `.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/avatarDefinition.schema.json:111-131`).
- Ameow does have a local SVG `clipPath`, but it is the head silhouette applied only to the eye `<g>` (`CompactMascot.tsx:180-205`). It clips children *inside* the head and is not an inverse ear mask or an ear-path subtraction. Applying it to an ear would retain the root portion rather than leave only the outside portion. No current call site applies a mask/clip/intersection to either ear slot.
- The current Ameow composition already has the information needed for an all-behind visual policy by composition alone: complete `backPaths`/`frontPaths`, matching node ids, and `headPath` are present in the scene (`.cindy-upstream/bible-strong-avatar-lab-175691a/packages/avatar-core/src/geometry.ts:49-60`; `compactMascotBehaviorRuntime.ts:44-51`). Painting each complete ear before `headPath` would naturally preserve only its outside-body pixels. It does not currently preserve that silhouette across poses because it follows the core’s whole-node `frontPaths` classification and paints those paths after the head (`CompactMascot.tsx:185-207`); index-based slotting also leaves the available ids unused (`CompactMascot.tsx:67-70`).

**Answer:** the original blanket “no existing capability” conclusion is too broad. Ameow already has a sufficient painter-order primitive for partial visual clipping of a complete ear that stays behind the head, and the scene carries enough path/id/head data to preserve that silhouette by composition. What is missing is a stable behind-head outcome across poses: core’s fixed contract may move the whole projected node to `frontPaths`, and there is no exposed per-node layer override; only if a pose must retain true front/back surface behavior within one crossing ear would a partial silhouette split be required.

### 4. Minimum capability gap (behavioral only)

The minimum gap is behavioral, not inherently fragment geometry: across every pose, the complete projected ear must remain in a behind-head paint outcome so the opaque circular body overpaints only its overlap while the outside pixels remain visible. The current core/host seam instead permits a whole-node front outcome; if preserving physically front-facing portions of a crossing ear is also required, the additional gap is per-ear partial surface occlusion at the body boundary rather than a whole-node `back`/`front` decision. No renderer/module/API/state design is proposed here.

## Caveats / Not Found

- Current Compact geometry is intentionally unchanged in this research; no ear shape, pose, animation, shell metric, or authority was altered.
- The comment at `MainWindowPresentationSurface.tsx:1227-1230` mentions a second 56px square clip, but the actual host style is `overflow: "visible"` at `:1230`; the functional shell clip is the inner panel at `:1151-1166`. This report relies on emitted JSX/styles, not that stale comment.
- Core’s binary classification is sufficient for the current neutral assertion (two back paths), and painter order already hides their overlap. If a future pose makes a node front, the whole projected node paints over the head; composition alone can avoid that only by retaining the complete node behind, while physically accurate crossing would need a partial surface boundary that the current contract does not expose.
- No external source was needed. The installed package/source-map inspection was read-only; only this report was written.
