## End-to-end ownership map

```text
Application DownloadJobService
  -> DownloadDiagnosticRecorder (typed events + bounded terminal summary)
  -> Electron runtime diagnostic sink
  -> RuntimeLogger -> console.log
  -> RuntimeLogController (memory + runtime-latest.log)
  -> SupportLogExport (allowlist/sanitization + newest 800 lines)
  -> Settings "Export support log" -> support-<timestamp>.txt

The same terminal summary follows a separate path:
DownloadJobService -> protocol terminal mapper -> Renderer/App outcome overlay
  -> "copy_error_diagnostics" -> incident-scoped report -> clipboard

Typed outcome telemetry is a third, machine-oriented path:
Runtime service -> telemetry sink -> configDir/telemetry/download-outcomes.jsonl
```

## Six conclusions

### 1. The complete producer/interface/storage/projection/UI/action/egress path is split across two user exports

**Producer and interface.** `DownloadJobService.executeJob()` creates one recorder using the Job trace ID and injected sink, records a single terminal event, attaches the bounded summary to typed failures, and otherwise preserves the original outcome (`src/application/download-job-service.ts:164-205`). The Job core records `download.prepared`, reports real attempt starts/results/fallbacks, and performs at most one typed auth-recovery retry (`src/application/download-job-service.ts:209-339`). The orchestrator deliberately reports only actual engine executions and candidate moves; skipped candidates produce no attempt event (`src/orchestration/download-orchestrator.ts:96-112`, `:169-178`, `:226-285`).

The event contract is closed and Electron-neutral: prepared, attempt, fallback, auth-recovery, and terminal event shapes contain stable facts rather than raw request/plan/error/context values (`src/application/download-diagnostics.ts:9-16`, `:56-137`). The recorder's sink interface is intentionally narrow and best effort (`src/application/download-diagnostics.ts:139-168`). The runtime passes that sink and the network-metadata callback into the application Job (`src/electron-runtime/service.ts:1460-1477`, `:1628-1697`).

The Renderer download client is the command/event boundary: queue and cancel methods invoke the typed desktop commands and subscriptions map `video-download-complete` back to feature payloads (`src/features/download/client.ts:149-209`). Electron's download IPC adapter allowlists those commands, decodes/validates the payload, and invokes the protocol-neutral Application API (`electron/downloadIpcAdapter.mts:19-23`, `:46-51`, `:194-250`).

**Session-log storage and Support Log export.** The default runtime sink is `createRuntimeLogDownloadDiagnosticSink(this.logger)` (`src/electron-runtime/service.ts:320-341`), whose `record()` serializes every typed event into one logger line (`src/electron-runtime/downloadDiagnosticSink.ts:7-13`). The Electron composition's runtime logger delegates to `logInfo("ElectronRuntime", message)` (`electron/main.mts:1445-1483`), and `logInfo()` writes to `console.log` (`electron/main.mts:422-428`). The runtime-log controller captures patched console methods into memory and appends each line to `runtime-latest.log` (`electron/runtimeLog.mts:110-144`, `:171-187`).

The Settings action invokes `export_support_log`, opens the returned parent directory, and reports success/failure (`src/pages/SettingsPage.tsx:660-686`); its button is rendered in the Support Log section (`src/pages/SettingsPage.tsx:2470-2484`). The command controller exposes only that command (`electron/supportLogCommands.mts:13-38`). Main wires config, dependency status, and recent runtime-line readers into `exportSupportLogFile()` (`electron/main.mts:1272-1287`, `:1819-1827`). The exporter projects environment/settings/runtime sections, takes the newest 800 runtime lines, sanitizes each line, and writes `support-<timestamp>.txt` (`electron/supportLogExport.mts:18-45`, `:46-83`).

**Incident Quick Copy.** App builds an `ErrorDiagnosticCopyRequest` from enqueue failures, typed download terminals, and transcode failures (`src/App.tsx:725-759`, `:1043-1068`, `:1359-1406`, `:1623-1650`) and calls `desktopCommands.invoke("copy_error_diagnostics", diagnostic)` (`src/App.tsx:761-773`). The callback reaches the center overlay (`src/App.tsx:2815-2836`), which exposes it only for failure outcomes (`src/presentation/main-window/MainWindowCenterOverlay.tsx:136-165`); the actual copy button invokes the callback (`src/components/ForegroundOutcomeOverlay.tsx:200-230`). The command controller normalizes, builds, and writes the report to the clipboard (`electron/errorDiagnosticCommands.mts:17-56`), with clipboard injection in Main (`electron/main.mts:1830-1843`).

The Quick Copy builder explicitly excludes session runtime-log excerpts and emits typed attempt/terminal facts first; only transcode/legacy failures without a typed summary receive one bounded evidence line (`electron/errorDiagnosticCopy.mts:242-301`). It formats attempts, terminal facts, optional evidence, and privacy notes (`electron/errorDiagnosticCopy.mts:320-399`). The protocol mapper supplies code/classification/category, safe URL, and terminal attempt summary while omitting raw downloader/process output (`src/protocol/download/ipcMappers.ts:337-372`).

The Settings diagnostics panel is not a third export: it only invokes the read-only snapshot command (`src/pages/SettingsPage.tsx:938-953`, `:2332-2352`; `electron/diagnosticsCommands.mts:14-40`).

### 2. Ownership and source of truth are explicit, but differ by egress

- **Typed diagnostic truth:** the Application owns the closed `DownloadDiagnosticEvent` union, attempt identity/history, and terminal summary; it is not an Event Bus or persistent store (`src/application/download-diagnostics.ts:9-16`, `:266-291`). `DownloadJobService` owns prepare-once, attempt, auth-recovery, and exactly-one-terminal lifecycle (`src/application/download-job-service.ts:27-35`, `:164-205`).
- **Runtime/session truth:** the Electron runtime owns the injected/default sink and runtime logger (`src/electron-runtime/service.ts:297-340`; `src/electron-runtime/downloadDiagnosticSink.ts:7-13`). `RuntimeLogController` owns in-memory/session-file capture, while Main owns the session path and capture initialization (`electron/runtimeLog.mts:61-75`, `:146-207`; `electron/main.mts:203-206`, `:434-451`, `:3661-3671`).
- **Support-export projection truth:** `supportLogExport` is the owner of the user-file projection. Its only data sources are config, runtime dependency status, and `readRecentRuntimeLogLines()` (`electron/supportLogExport.mts:18-45`); it does not read the typed telemetry JSONL or the Application terminal object. Therefore `[recent-runtime-log]` is session-log truth, not typed-terminal truth.
- **Quick Copy projection truth:** the request/terminal payload from Renderer is normalized and projected by `errorDiagnosticCopy`; the report's own contract says it contains typed incident facts and ordered attempts, never whole-session runtime lines or open context bags (`src/types/errorDiagnostics.ts:51-79`; `electron/errorDiagnosticCopy.mts:248-301`).
- **Structured telemetry truth:** runtime telemetry is separately written to `configDir/telemetry/download-outcomes.jsonl` (`src/electron-runtime/downloadTelemetry.ts:10-27`, `:29-57`). The telemetry event intentionally persists `errorMessage: null` and stores code/classification/category plus bounded attempts (`src/download-capabilities/telemetry.ts:192-233`); runtime records it once for non-success terminals and after successful download/transcode follow-up (`src/electron-runtime/service.ts:1759-1796`, `:1861-1895`). It is not an input to Support Log export.
- **Renderer UI truth:** the feature model owns queue membership/progress and a bounded terminal tombstone guard; protocol DTOs stop at the client boundary (`src/features/download/model.ts:3-10`, `:60-95`). The client classifies typed failure first and only uses raw cancelled-text parsing for legacy payloads (`src/features/download/client.ts:99-132`). The reducer removes terminal traces from active state and leaves bounded tombstones (`src/features/download/reducer.ts:195-212`).

### 3. Filtering, redaction, correlation, and retention/retry behavior are bounded but not semantically filtered at Support Log egress

**Correlation and typed bounds.** A recorder has one caller-supplied Job `traceId`; each real attempt gets a monotonic `attemptIndex` and `traceId:index` `attemptId` (`src/application/download-diagnostics.ts:170-205`, `:281-324`). Attempt history is capped at `MAX_ATTEMPT_HISTORY = 8` (`src/application/download-diagnostics.ts:178`, `:285-290`). The terminal summary snapshots the attempts and is idempotent (`src/application/download-diagnostics.ts:383-423`). The same prepared plan and opaque Job context are reused across attempts and the at-most-one auth retry; only per-attempt context may observe refreshed auth (`src/application/download-job-service.ts:109-115`, `:294-339`).

**Redaction and projection.** The shared sanitizer reduces URLs to origin, hides cookies/auth/proxy/token values and local paths, bounds strings, and recursively bounds arrays/depth; callers must allowlist first (`src/core/diagnostics/safe-diagnostic.ts:81-133`, `:159-207`). Runtime-log ingest sanitizes every message and caps each line at 4,000 characters (`electron/runtimeLog.mts:110-120`); Support Log sanitizes again at egress (`electron/supportLogExport.mts:37-44`). Environment path values and sensitive setting paths/endpoints become presence booleans (`electron/supportLogSnapshot.mts:24-51`, `:86-111`); runtime dependency paths become presence booleans with bounded errors (`electron/supportLogSnapshot.mts:140-164`).

**Retention and clear.** Runtime memory defaults to 1,500 lines and exported reads default to 800 (`electron/runtimeLog.mts:61-66`; Main constants `electron/main.mts:203-206`). `initializeRuntimeLogCapture()` clears the memory buffer, overwrites the session file with a header, and then patches console methods (`electron/runtimeLog.mts:146-187`); Main calls it once after app readiness and user-data directories are prepared (`electron/main.mts:3661-3671`). Reads await pending writes, use the file when present, fall back to memory on missing/read failure, and return the newest bounded slice (`electron/runtimeLog.mts:189-207`). There is no runtime-log clear command in the renderer command vocabulary (`src/types/electronBridge.ts:10-53`), so the proven clear boundary is session initialization, not a Settings action. Renderer terminal tombstones are capped at 128; an explicit `queueAccepted` for a reused trace clears one guard, while `reset` clears the whole queue model (`src/features/download/model.ts:82-95`; `src/features/download/reducer.ts:81-92`, `:195-212`).

**Retry lifecycle.** Engine fallback/auth recovery are part of one Download Job and its typed chronology (`src/orchestration/download-orchestrator.ts:226-285`; `src/application/download-job-service.ts:309-339`). Transient/section retries inside yt-dlp retain bounded stderr tails and emit semantic timing lines rather than dumping raw child output (`src/electron-runtime/ytDlpDownload.ts:349-395`, `:456-503`, `:505-558`). Transcode is a separate runtime queue: `FAILED_TRANSCODE_RETENTION_LIMIT` is 20, failed tasks are retained to that cap, retry moves a failed task back to pending and clears error/failure fields, and remove discards it (`src/electron-runtime/service.ts:254`, `:969-1003`, `:1026-1062`); the Renderer invokes retry through `retry_transcode` (`src/App.tsx:1104-1121`, `electron/videoDownloadCommands.mts:31-40`, `:68-78`).

**Missing semantic filter.** Support export only tails and sanitizes the runtime lines; it does not classify, correlate, deduplicate, or project `[DownloadDiagnostic]` records (`electron/supportLogExport.mts:31-45`, `:67-73`). Consequently, retention/redaction limits privacy and size but do not remove repetitive event lines.

### 4. Diagnostic reinsertion into session logging is the direct, proven noise cause

The direct reinsertion is one line: `record(event)` calls `logger.log(\`>>> [DownloadDiagnostic] ${JSON.stringify(event)}\`)` (`src/electron-runtime/downloadDiagnosticSink.ts:7-13`). With no injected sink in Main's runtime construction, `AmeowElectronDownloadRuntime` selects that runtime-log sink by default (`src/electron-runtime/service.ts:320-341`; Main provides a logger but no `diagnosticSink`, `electron/main.mts:1445-1483`). That logger reaches `console.log` (`electron/main.mts:422-428`), and the active console patch appends it to the session buffer/file (`electron/runtimeLog.mts:171-186`). Support export then copies the newest lines into `[recent-runtime-log]` after text sanitization but without semantic filtering (`electron/supportLogExport.mts:42-44`, `:67-73`).

The volume amplification is inherent in the current event lifecycle: a Job may produce `download.prepared`, one start/result pair per real attempt, fallback and auth-recovery markers, and one terminal event (`src/application/download-diagnostics.ts:56-137`; `src/application/download-job-service.ts:254-339`, `:383-423`). This proves repetitive typed event lines are reinserted into the session evidence consumed by Support Log. It does **not** prove that raw yt-dlp stderr is dumped wholesale: yt-dlp buffers stderr per attempt, sanitizes it, and logs only bounded tails/timing fields (`src/electron-runtime/ytDlpDownload.ts:349-395`, `:505-558`).

### 5. The smallest suitable direction is projection-only tightening at the Support Log boundary

- **Projection-only tightening (recommended for this target):** Support export already has an explicit allowlist/projection boundary and already owns the `[recent-runtime-log]` section (`electron/supportLogSnapshot.mts:7-12`; `electron/supportLogExport.mts:28-45`, `:46-73`). Tightening that projection to suppress or reduce repetitive `DownloadDiagnostic` records is the smallest local architectural change and leaves Application event chronology, runtime logging, typed Quick Copy, and existing retry/fallback/auth semantics intact.
- **Dependency-direction adjustment (cleaner long-term seam, larger scope):** the runtime sink currently points Application diagnostics into a developer/session logger (`src/electron-runtime/downloadDiagnosticSink.ts:7-13`; `src/electron-runtime/service.ts:320-341`). Separating those dependencies would make session logging and typed diagnostics independently owned, but it is broader than the current readability target and is not required to establish a safe user export.
- **Separate storage:** a new diagnostic store is unnecessary for the current requirement. Typed telemetry already has an append-only JSONL store with bounded, non-raw outcome facts (`src/electron-runtime/downloadTelemetry.ts:10-57`; `src/download-capabilities/telemetry.ts:215-233`), while Quick Copy already carries the incident terminal summary without session lines (`src/types/errorDiagnostics.ts:51-79`; `electron/errorDiagnosticCopy.mts:248-301`). A third store would duplicate lifecycle/retention ownership rather than solve the current projection problem.
- **Other smaller alternative:** filtering only the `[DownloadDiagnostic]` records at the existing Support Log projection boundary is the narrowest variant of projection-only tightening; preserving other semantic runtime/timing lines avoids collapsing useful developer evidence. No broad runtime-log rewrite or yt-dlp collection refactor is warranted by the proven chain.

### 6. `DownloadDiagnostic` itself does not need a semantic change; later planning should address boundaries

The recorder already provides the needed one-failed-task facts: stable trace/attempt correlation, bounded attempt history, safe fields, real-attempt-only reporting, explicit fallback/auth-recovery chronology, and exactly one terminal summary (`src/application/download-diagnostics.ts:9-16`, `:266-291`, `:304-424`; `src/orchestration/download-orchestrator.ts:96-112`). `DownloadJobService` isolates sink failures and keeps diagnostics observational, so changing event semantics to fix export noise would risk disturbing correct retry/fallback/auth behavior (`src/application/download-job-service.ts:135-139`, `:164-205`; `src/orchestration/download-orchestrator.ts:169-178`).

The boundary that needs a later product decision is whether Support Log should project these typed events at all, and if so which event classes/fields are useful there. The evidence points to the Support Log projection/sink boundary—not the recorder's event union—as the place to resolve readability; Quick Copy's existing incident-scoped builder already supplies the minimum typed terminal report and explicitly excludes session logs (`electron/errorDiagnosticCopy.mts:242-301`). A future planning task should preserve the current typed chronology and decide the exact Support Log filter/correlation policy; it should not assume a new storage system or a raw-process logging redesign.

## Explicit caveats

1. The baseline check compared committed Git blobs only; all cited chain files matched exactly between `f1b4991c58982fc5a896e61bf58840c2aeec9cfa` and `9440310326382691217e606664ef53de001dd9fa`. The working tree contains untracked task/tmp directories, so this report does not treat snapshots or untracked artifacts as application evidence.
2. Runtime-log capture is asynchronous for file appends (`electron/runtimeLog.mts:122-131`), but `readRecentRuntimeLogLines()` awaits the write chain before reading (`electron/runtimeLog.mts:189-203`); the report therefore treats exported lines as the settled session file/buffer view, not an instantaneous console race.
3. “No semantic filtering” is scoped to the Support Log's recent-runtime-log projection: sanitization, line/array bounds, and allowlist projections are present. Quick Copy and typed telemetry have stronger incident/schema projections and are not evidence that Support Log shares their source of truth.
4. The diagnostics panel's eight-line recent snapshot is read-only and separate from the Support Log file (`electron/diagnostics.mts:197-214`, `:335-353`; `electron/diagnosticsCommands.mts:18-40`); it should not be counted as another export entry point.
